# ai-orchestrate

Локальный личный агент для GitHub-проектов. Панель управляет задачами, Codex CLI, Jev, проверками, рабочими ветками/worktree, журналом и финальным слиянием. По умолчанию Codex ничего не сливает без кнопки подтверждения.

## Быстрый старт

Нужны Python 3.10+, Git, Codex CLI и (для работы с GitHub) GitHub CLI. Одна команда проверяет
всё сразу, сама дописывает в PATH каталоги, где инструменты обычно лежат, и подсказывает, чем
закрыть каждую дыру:

```bash
python -m ai_orchestrate doctor          # что есть, чего нет и как исправить
python -m ai_orchestrate doctor --json   # тот же отчёт машиночитаемым JSON
python -m ai_orchestrate setup --install --repo ./project --autofill
```

`setup` делает три вещи: чинит PATH, при `--install` ставит отсутствующие Codex CLI / GitHub CLI
известным для системы установщиком и при `--autofill` подбирает настройки по выбранному
репозиторию (команды проверок, базовая ветка, согласованные лимиты). Без `--install` и
`--autofill` команда только показывает план и ничего не меняет.

Проверить окружение вручную по-прежнему можно так:

```bash
codex --version
codex login status
gh --version
gh auth status
```

Codex CLI использует уже настроенный вход Codex. Если он авторизован через ChatGPT, панель вызывает модели через этот CLI и не требует OpenAI API key. Панель не автоматизирует окно ChatGPT и не использует cookies/браузер: она запускает `codex exec` в выделенном локальном worktree. Если CLI ещё не авторизован, выполни `codex login`. Для GitHub войди через `gh auth login`.

Запуск панели:

```bash
python -m ai_orchestrate ui --workspace-root ~/work
```

На Windows можно запустить `start.bat` двойным щелчком. Для нескольких репозиториев укажи общую папку через `--workspace-root`, например `start.bat --workspace-root C:\work`. Выбираемые репозитории должны находиться внутри этой области; пути через символические ссылки за её пределы отклоняются.

## Типичный сценарий в панели

1. Выбери Git-репозиторий и введи задачу. Для GitHub issue/PR вставь `#123` или URL и нажми **Загрузить**. Поддерживаются открытые issues и PR этого репозитория; PR из fork для автоматической записи отклоняются.
2. Укажи локальные команды проверок (по одной на строку). Панель предложит обнаруженные проверки, но перед запуском проверь, что они действительно подходят проекту.
3. Нажми **Автонастройка** — панель сама подставит репозиторий, команды проверок, базовую ветку и согласованные лимиты. Дальше выбери полный цикл или экономный режим, исполнителя, модели, GitHub-цель и способ финального решения. Нажми **Сохранить настройки** — настройки также сохраняются автоматически при изменениях.
4. Агент создаст отдельную ветку и Git worktree, выполнит задачу, локальные проверки и, в полном цикле, независимое read-only ревью. Исходный checkout не редактируется.
5. После успешных проверок выбери один из режимов слияния:
   - **После кнопки «Подтвердить слияние»** — безопасный режим по умолчанию. Кнопка выполнит fast-forward в локальную базовую ветку либо push/создание PR и merge через GitHub CLI.
   - **Автоматически после финального APPROVE от Jev** — Jev отдельно проверит ограниченный diff, проверки и итог независимого ревью. Только `APPROVE` запускает интеграцию автоматически. `HOLD` или `REJECT` останавливают автослияние и показывают явную кнопку ручного подтверждения; для REJECT она помечена как override.

Слияние не нужно делать в терминале вручную. В локальном режиме агент делает только `git merge --ff-only`: если целевая ветка изменилась либо исходный checkout стал грязным, слияние останавливается. В GitHub-режиме агент создаёт или обновляет PR и не использует обход branch protection. Если обязательные GitHub checks ещё идут, `gh pr merge --auto` ставит merge в очередь, когда репозиторий разрешает auto-merge; итоговое решение о готовности и approvals остаётся за GitHub. Если правила репозитория не разрешают слияние, панель показывает ошибку и сохраняет рабочую ветку.

Для задачи из GitHub выбери **GitHub · pull request и merge** (кнопка загрузки issue/PR выбирает эту цель автоматически). Для обычной задачи можно выбрать локальное слияние или PR в GitHub. Для локального слияния в базовой ветке должны быть настроены `git config user.name` и `git config user.email`.

Если проверки/ревью не прошли, Jev не одобрил задачу или слияние не удалось, рабочая ветка остаётся доступной для осмотра. Кнопка **Удалить ветку и worktree** удалит её после отдельного подтверждения.

## Готовность, автоустановка и ключ Jev

Панель показывает состояние окружения в блоке **«Готовность и доступ»**: по каждому инструменту
виден статус, путь, версия и конкретное действие. То, что ставится автоматически (Codex CLI,
GitHub CLI), ставится кнопкой прямо в панели — вывод установщика показывается построчно. Вход
(`codex login`, `gh auth login`) интерактивный, поэтому панель не выполняет его сама, а отдаёт
команду кнопкой «Скопировать».

Что чинится само:

- PATH дополняется каталогами, где codex/gh/node обычно оказываются после установки
  (`~/.local/bin`, `~/.bun/bin`, npm-префикс, `/opt/homebrew/bin`, WinGet/scoop и т. п.);
- проверки, базовая ветка и лимиты подбираются кнопкой **«Автонастройка»** по выбранному
  репозиторию; кнопка **«Сбросить к значениям по умолчанию»** возвращает заводские значения;
- при отсутствии ключа Jev роутер и политика слияния автоматически переключаются на бесплатные
  локальные варианты, чтобы задача не упиралась в недоступную функцию.

**Ключ Jev** вставляется в отдельное поле «Ключ Jev · TYPESAFE_API_KEY» слева. Он сохраняется в
`~/.ai-orchestrate/jev-key` с правами `0600`, действует сразу без перезапуска панели и
никогда не попадает ни в `settings.json`, ни в промпты, ни в окружение Codex CLI. Панель
показывает только маску (`tsk_…CDEF · 29 символов`) и никогда не возвращает ключ обратно.
Альтернатива без панели: `python -m ai_orchestrate jev-key set` (ключ читается из stdin без
отображения), `jev-key status`, `jev-key clear`. Экспортированная `TYPESAFE_API_KEY` имеет
приоритет над файлом.

## Исполнитель: Codex CLI или OpenAI-совместимый API

В блоке «Как работаем» выбирается исполнитель:

- **Codex CLI** — по умолчанию. Использует авторизацию `codex login` (в том числе вход через
  ChatGPT) и не требует OpenAI API key.
- **OpenAI-совместимый API** — работает без Codex CLI, если кредиты Codex закончились или
  подписки нет. Нужны имя модели и адрес API: OpenAI (`https://api.openai.com/v1`),
  OpenRouter (`https://openrouter.ai/v1`), Ollama (`http://127.0.0.1:11434/v1`) или
  LM Studio (`http://127.0.0.1:1234/v1`). Для внешних адресов обязателен ключ; локальные
  серверы работают без ключа.

API-исполнитель получает тот же ограниченный набор инструментов, что и Codex: чтение файла,
список каталога, запись файла, замена фрагмента, запуск команды и `finish`. Пути ограничены
worktree задачи, этапы планирования и ревью работают read-only, опасные команды отклоняются,
а число раундов и токенов ограничено настройками. Расход токенов пишется в тот же token ledger.

Ключи провайдеров хранятся так же, как ключ Jev: отдельные файлы с правами `0600`
(`~/.ai-orchestrate/openai-key`, `~/.ai-orchestrate/openrouter-key`), только маска в UI,
никогда в `settings.json`. Без панели:

```bash
python -m ai_orchestrate keys status
python -m ai_orchestrate keys set openai      # ввод без эха
python -m ai_orchestrate keys clear openrouter
```

## Мост ChatGPT (вручную, без автоматизации)

Панель не управляет окном ChatGPT, не использует cookies и не читает чужие ответы
программно — это запрещено условиями использования OpenAI. Вместо этого есть ручной мост
«Человек в контуре»:

1. После запуска, который остановился на непройденных проверках, нажми **Собрать промпт**
   в панели «Мост ChatGPT». Панель соберёт один текст: задача, ограниченный diff, `git status`
   и точный вывод падающих проверок.
2. Скопируй его в приложение ChatGPT и получи ответ блоками файлов: `### FILE: путь` с полным
   содержимым или `*** Begin Patch` / `*** Update File:` / `*** Add File:` / `*** Delete File:`.
3. Вставь ответ целиком и нажми **Применить ответ и проверить**. Панель разберёт блоки,
   применит их только внутри изолированного worktree (пути наружу отклоняются), снова запустит
   проверки проекта и, если всё зелёное, закоммитит изменения и предложит подтвердить слияние.

Если проверки не прошли, слияние недоступно: попроси исправленный ответ и повтори шаг 3.
Ответ без блоков файлов и патч с несовпавшим контекстом отклоняются с понятной причиной,
файлы при этом не меняются.

## Проекты, которые уже видел Codex

Кнопка **▾** рядом с полем «Папка проекта» показывает каталог проектов. Он собирается из трёх
источников: история сессий Codex CLI (`$CODEX_HOME` или `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`,
рабочая папка берётся из записи `session_meta`), журнал запусков панели и сканирование рабочей
области на Git-репозитории. Для каждого проекта видно число сессий Codex, время последнего
использования и ветку. Проекты вне `--workspace-root` показываются, но остаются недоступными для
выбора: панель не выходит за разрешённую область, поэтому для них подсказывается перезапуск с
нужным `--workspace-root`.

## Настройки и сохранение

Настройки панели хранятся локально в `~/.ai-orchestrate/settings.json` (Windows: в домашней папке пользователя); секреты туда не записываются. В панели сохраняются:

- выбранный репозиторий, команды проверок и отдельный текст постоянного контекста для каждой папки;
- режим, профессия исполнителя, локальный/Jev-роутер и стартовая полоса;
- исполнитель (`codex` или `api`), имя API-модели, адрес API и число раундов инструмента;
- Luna/Sol/reviewer model names, число исправлений/вызовов, prompt/token budgets и таймауты;
- базовая ветка, префикс веток и каталог worktree;
- цель слияния (локальная/GitHub), политика подтверждения/JeV, merge method, ожидание GitHub checks и удаление ветки;
- включение краткого журнала запусков, а также настраиваемые пути журнала и token ledger (пустое поле оставляет путь по умолчанию).

В панели можно явно нажать **Сохранить настройки**; основные поля также сохраняются автоматически после изменения. Кнопка **Автонастройка** заполняет всё, что определяется из репозитория и окружения, и печатает отчёт: что подобрано, что оставлено как было и что стоит решить вручную. Текст самой задачи и содержимое GitHub не сохраняются в файле настроек. Постоянный проектный контекст привязан к выбранной папке и добавляется только к задачам этого проекта.

Jev требует API-ключ: его можно вставить в поле «Ключ Jev» в панели (сохранится в `~/.ai-orchestrate/jev-key`, 0600) или экспортировать как `TYPESAFE_API_KEY` до запуска. Ключ не показывается, не хранится в `settings.json` и не передаётся в Codex CLI. Автоматический режим Jev недоступен без ключа и требует полного цикла с независимым ревью. Codex и GitHub используют свои входы (`codex login`, `gh auth login`); их пароли и токены панель не запрашивает.

Данные по умолчанию:

- настройки: `~/.ai-orchestrate/settings.json`;
- журнал кратких итогов: `~/.ai-orchestrate/journal.jsonl`;
- telemetry Codex: `~/.ai-orchestrate/usage.jsonl`;
- изолированные worktree: `~/.ai-orchestrate/worktrees/`;
- ключ Jev: `~/.ai-orchestrate/jev-key` (0600, единственный секрет на диске).

Переменная `AI_ORCHESTRATE_HOME` переносит весь этот каталог целиком — удобно для теста или
отдельного профиля.

Журнал не сохраняет задачу или diff: в нём остаются статус, репозиторий, ветка, GitHub URL, перечень изменённых файлов, решение Jev, модельные вызовы и token totals. Ledger usage хранит только дату, роль, модель и числа токенов.

## Бюджет и расход

Полный цикл обычно использует три вызова Codex (планировщик, исполнитель, ревьюер), дополнительные исправления ограничены настройками. Экономный режим запускает исполнителя и локальные проверки без планировщика и независимого ревью. Локальные тесты не расходуют модельные вызовы. Jev для первичного triage и отдельный финальный Jev gate — внешние вызовы, они не входят в Codex usage ledger.

Панель показывает реальные `input / cached input / output` токены, если их вернул Codex CLI. `input_tokens` уже включает cached input. Ограничения бюджета остановят **следующие** вызовы; активный ход модели может перейти лимит, это не hard cap аккаунта и не оценка цены в евро. Цена зависит от тарифов ChatGPT/Codex и настройки биллинга провайдера.

Headless-команды также остаются доступны:

```bash
python -m ai_orchestrate doctor
python -m ai_orchestrate usage
python -m ai_orchestrate run "Исправь обработку ошибок" --repo ./project --check "pytest -q" --max-attempts 2 --max-model-calls 2 --max-run-tokens 30000
```

CLI-команда `run` — отдельный одноразовый режим старой совместимости: она работает в указанном checkout и не включает GitHub/worktree/слияние панели. Для GitHub-агента используй `ui`.

## Что защищает рабочую копию

- Модель редактирует только выделенный Git worktree. Базовый checkout остаётся нетронутым до подтверждённого merge.
- Merge невозможен без успешных обязательных проверок; полный цикл дополнительно требует первой строки `PASS` у независимого read-only ревью.
- Перед автоматическим commit блокируются потенциально секретные файлы (`.env`, credentials, private keys и подобные имена).
- Локальная цель сливается только fast-forward и только если ветка/HEAD совпадают с начальным снимком и checkout чист.
- GitHub push/merge разрешается только финальным Jev `APPROVE` либо явной кнопкой. Администраторский обход проверок (`--admin`) не используется.
- Issue/PR-контент считается недоверенными данными. Ключи не передаются моделям через prompt; Codex CLI исключает Jev API key из своего дочернего окружения.
- UI ограничивает доступ к папкам указанной рабочей областью и блокирует cross-origin POST. Сам HTTP-сервер не имеет пользовательской аутентификации: оставляй его на `127.0.0.1` и не публикуй в недоверенную сеть. `--host 0.0.0.0` используй только для защищённого preview.

## Проверки проекта

```bash
python -m compileall -q ai_orchestrate tests
python -m unittest discover -s tests -v
```

Тесты покрывают обнаружение инструментов и автоустановку (установщик подменяется заглушкой),
хранение ключа Jev, чтение истории сессий Codex, автоподбор настроек и новые HTTP-эндпоинты
панели.

Тесты не выполняют реальные вызовы Codex/Jev и не отправляют PR в GitHub; внешние интеграции проверяются через моки. Живой запуск зависит от установленного Codex CLI, входов `codex`/`gh`, сети и доступных моделей.
